# RAG 知识库全链路

## 一、RAG 核心流程

### 标准 RAG 管线

```
文档摄入                          查询检索
    │                                │
    ├─ 加载（PDF/Word/HTML/Markdown）  ├─ Query 改写（HyDE/多查询）
    ├─ 分片（Chunking）               ├─ Embedding（查询向量化）
    ├─ Embedding（向量化）             ├─ 向量检索（Top-K）
    ├─ 存入向量数据库                  ├─ Rerank（重排序）
    │                                ├─ 上下文组装
    │                                └─ LLM 生成回答
```

### 为什么需要 RAG
- **知识时效性**：LLM 训练数据有截止日期，RAG 可接入实时知识
- **领域知识**：企业内部文档 LLM 没见过，RAG 注入领域知识
- **减少幻觉**：有据可查的回答比模型自由生成更可信
- **成本**：比微调模型便宜，知识更新只需更新向量库

## 二、文档分片（Chunking）

### 分片策略

#### 固定长度分片
- 按固定字符数切分（如 500 字符）
- 简单但可能切断语义
- 适合格式统一的文档

#### 递归分片（推荐）
- **语义优先级降级**：段落 → 行 → 句子 → 逗号 → 空格 → 字符
- 先按段落切，段落太长按行切，行太长按句子切...
- **重叠机制**：相邻 chunk 保留 50-200 字符重叠，避免边界信息丢失

#### 九级语义优先级降级（J.A.R.V.I.S. 实现）
```
段落(\n\n) → 行(\n) → 句子(。！？) → 分号(；) → 逗号(，) → 空格( ) → 字符
```
每降一级，chunk 大小减半，直到满足目标长度。

### Chunk 大小权衡

| Chunk 大小 | 优点 | 缺点 |
|-----------|------|------|
| 小（200 字符） | 检索精度高 | 上下文不完整，可能丢失关键信息 |
| 中（500 字符） | 精度与完整性平衡 | —— |
| 大（1000+ 字符） | 上下文完整 | 检索精度低，token 消耗大 |

**选 500 字符的理由**：
- Embedding 质量 × 检索精度 × 上下文完整性的平衡点
- 大多数 Embedding 模型对 500 字符左右的文本效果最佳
- 500 字符 ≈ 200-300 token，检索 5 个 chunk ≈ 1500 token 上下文

### 特殊文档处理
- **表格**：转为 Markdown 表格或 JSON
- **代码**：按函数/类边界切分
- **PDF**：OCR + 版面分析，提取标题层级
- **HTML**：去除标签，保留标题结构

## 三、Embedding 模型

### 主流模型对比

| 模型 | 维度 | 中文支持 | 特点 |
|------|------|---------|------|
| text-embedding-v3 (DashScope) | 1024 | ✅ 优秀 | 国内骨干网低延迟 |
| BGE-large-zh | 1024 | ✅ 优秀 | 开源，可本地部署 |
| BGE-m3 | 1024 | ✅ 多语言 | 支持稠密+稀疏+ColBERT |
| OpenAI text-embedding-3-small | 1536 | ⚠️ 一般 | 国际标准 |
| OpenAI text-embedding-3-large | 3072 | ⚠️ 一般 | 最高精度 |
| Cohere embed-v3 | 1024 | ✅ 好 | 支持多语言 |

### 选型考量
- **技术栈一致性**：用 DashScope LLM 就用 DashScope Embedding，减少跨服务延迟
- **国内骨干网**：国内部署选 DashScope/BGE，避免 OpenAI 网络延迟
- **本地部署**：BGE 系列开源，可本地推理
- **多语言**：BGE-m3 或 Cohere

### Embedding 质量评估
- **MTEB 榜单**：标准评估集，覆盖检索/分类/聚类等任务
- **领域适配**：通用模型在特定领域（医疗/法律）可能效果差，需要微调
- **维度选择**：高维度 ≠ 高质量，1024 维通常够用

## 四、向量数据库

### 主流对比

| 数据库 | 类型 | 特点 | 适用场景 |
|--------|------|------|---------|
| ChromaDB | 嵌入式 | 轻量，Python 原生 | 原型/小规模 |
| Milvus | 分布式 | 高性能，可扩展 | 生产级/大规模 |
| Pinecone | 云服务 | 全托管，免运维 | 不想运维 |
| FAISS | 库 | Meta 开源，纯本地 | 本地推理 |
| PGVector | PostgreSQL 扩展 | 复用 PG 生态 | 已有 PG |
| Redis | 内存数据库 | 低延迟 | 实时检索 |

### 选型考量
- **规模**：< 100 万向量用 ChromaDB/FAISS；> 100 万用 Milvus
- **运维**：不想运维用 Pinecone；已有 PG 用 PGVector
- **延迟**：实时要求高用 Redis；离线用 FAISS

## 五、检索策略

### 基础检索
- **稠密检索**：Query Embedding → 余弦相似度 → Top-K
- **稀疏检索**：BM25 / TF-IDF → 关键词匹配
- **混合检索**：稠密 + 稀疏加权融合

### Query 改写

#### HyDE（Hypothetical Document Embedding）
- 先让 LLM 生成一个"假想回答"
- 用假想回答的 Embedding 检索（比原始 Query 更接近目标文档）
- 适合 Query 太短或太模糊的场景

#### 多查询生成
- LLM 把一个 Query 改写成多个不同角度的 Query
- 分别检索后合并去重
- 提高召回率

### Rerank（重排序）

#### 为什么需要 Rerank
- 向量检索是"近似"检索，Top-K 里可能有噪声
- Rerank 模型对 Query-Document 对做精细打分，重排结果

#### Rerank 模型
| 模型 | 特点 |
|------|------|
| BGE-reranker | 开源，中英文支持好 |
| Cohere Rerank | 商用，效果好 |
| DashScope Rerank | 国内低延迟 |
| Cross-Encoder | 通用方法，精度高但慢 |

#### 选 DashScope 而非 BGE 的理由
- 技术栈一致性（LLM + Embedding + Rerank 同一服务）
- 国内骨干网延迟低
- 不需要本地部署 GPU

### 上下文组装
- **Top-K 选择**：通常取 Rerank 后 Top 3-5 个 chunk
- **去重**：相似度过高的 chunk 去重
- **窗口扩展**：取 chunk 前后各一个 chunk 作为上下文
- **Token 预算**：总上下文不超过 LLM 窗口的 1/3

## 六、检索准确率评估

### 评估方法

#### Recall@K
- 在标注的"正确文档"中，Top-K 检索结果命中了多少
- Recall@5 = 正确文档在 Top 5 的比例

#### MRR（Mean Reciprocal Rank）
- 第一个正确文档的排名的倒数
- MRR = 1/n × Σ(1/rank_i)

#### 端到端评估
- 给 N 个测试问题，每个问题标注正确答案
- LLM 生成回答后，人工或 LLM 评判是否正确
- 准确率 = 正确数 / N

### 小规模评估的局限性
- 15 个测试问题的小规模评估只能给参考，不能下绝对结论
- 需要 100+ 测试问题才能达到统计显著性
- 坦诚承认局限性比夸大准确率更可信

### 评估最佳实践
- **诚实报告**：说"基于 15 个测试问题，准确率 90%"而非"准确率 90%"
- **错误分析**：分析错误案例，找出是检索问题还是生成问题
- **A/B 测试**：改变参数（chunk 大小/Rerank 模型）后对比

## 七、高级 RAG 模式

### Multi-modal RAG
- 图片/表格也做 Embedding 检索
- 多模态模型（如 GPT-4V）理解图片内容
- 适用于含图表的文档

### GraphRAG
- 构建知识图谱（实体 + 关系）
- 检索时不仅找相关 chunk，还找关联实体
- 适用于需要多跳推理的场景

### Self-RAG
- LLM 自主决定是否需要检索
- 检索后自主评估结果质量
- 不相关时拒绝使用检索结果

### Corrective RAG（CRAG）
- 检索结果质量评估
- 质量差时触发 Web 搜索补充
- 质量好时直接使用
